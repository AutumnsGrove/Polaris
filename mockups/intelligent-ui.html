1 · In context

A ui block sits between prose, like a mermaid fence does today. The prose carries the reasoning; the block carries the part that is really a table, a procedure, or a number. Citations bind to the same numbered sources as the text.

HERO

Oracle read it as a comparison → one block, framed by prose.

2 · Block gallery

The starter vocabulary, two takes where the phone layout is a real decision. Option A / B are visual alternatives for the same fence lines.

Recommendation up front: compare → B (cards) on phones (a 3-column table forces sideways scrolling), steps → A (rail), timeline → A (rail), callout → A. The same block can switch layout by viewport, so the model never picks a layout — only the data.

3 · "Mermaid Plus" — a flow block

Mermaid stays (sequence, ER, gantt, anything graph-shaped it already does). The gap is the most common case — a process or decision chain — where mermaid's output is a desktop-shaped graph squeezed onto a phone. A flow block is vertical-first, each node is a tappable card that expands to detail, and nodes can carry sources.

Scope guard: flow is for processes and decision chains up to ~8 nodes. Anything bigger, or any other graph type, stays mermaid. Node/edge lines are a stream-friendly shape: each node card can appear the moment its line completes (edges attach when both ends exist).

4 · Streaming — the whole "compiler"

The claim in the plan: a stream of whole lines needs no incremental JSON parser. Each completed line becomes a component; the trailing partial line is held back (shown as a shimmer) until its newline. Hit replay. The stream deliberately includes an unknown component and a malformed line — both degrade quietly instead of breaking the answer.

5 · Oracle integration


Oracle already reads each message with one Jev call carrying ~20 questions. Adding a ui question costs almost nothing. Its job: say whether a visual block beats prose and which one, then nudge the model with the exact syntax for that block — a just-in-time few-shot.
