1 · In context

A ui block sits between prose, like a mermaid fence does today. The prose carries the reasoning; the block carries the part that is really a table, a procedure, or a number. Citations bind to the same numbered sources as the text.

HERO

3 · "Mermaid Plus" — a flow block

Mermaid stays (sequence, ER, gantt, anything graph-shaped it already does). The gap is the most common case — a process or decision chain — where mermaid's output is a desktop-shaped graph squeezed onto a phone. A flow block is vertical-first, each node is a tappable card that expands to detail, and nodes can carry sources.

Five more blocks, picked for what Polaris is specifically about: sourcing and phone-sized reading. Several reuse an Oracle check that already exists, so they add a nudge, not a new Jev question (see the table at the end).

Supports

Disputes

 "verdict":"misleading"}
{"+":"Manufacturer calls it espresso-style","cite":[1]}
{"-":"Brews at ~1.5 bar; espresso is ~9 bar","cite":[2,3]}

The sourcing-is-the-product block. Verdicts mirror the existing claim_check nudge (true / false / misleading / unverified) plus mixed. Reuses +/- child lines from procon.

NEW

quote — a sourced pull-quote

{"c":"quote","text":"Use water just off the boil…",
 "by":"Brewing guide","cite":[3]}

Trust marks are never model-written. The “found in source” badge comes from the per-claim verification Polaris already runs, checked against the cited source's text. A quote that fails it renders without the badge, so the model can't claim a verification it didn't get.

NEW

5 · Streaming — the whole "compiler"

A stream of whole lines needs no incremental JSON parser. Each completed line becomes a component and the trailing partial line is held back (the shimmer) until its newline. Pick a scenario and hit replay. The mixed one includes an unknown component and a malformed line, which degrade quietly. In the flow one, nodes appear as their lines arrive and edges attach once both ends exist.

6 · Mermaid, streamed


Mermaid is an external library, so it can't render inside a half-written line. But it doesn't need to. Today a diagram waits for the whole turn (ChatTurnView.svelte gates on !turn.streaming). That gate exists to avoid a failure flash on an unclosed fence, not because mermaid can't cope with partial input. Re-rendering at each complete line, and keeping the last good result when a prefix doesn't parse, gets a diagram that builds up as it's written.


Measured (mermaid 11.12, real library, headless Chromium): every line-boundary prefix of a flowchart (9/9), sequence diagram (8/8) and gantt (8/8) parsed and rendered; an ER diagram failed only inside an open { … } attribute block (5/8), which "keep the last good render" absorbs. Render time per attempt: median ~29 ms, max ~52 ms for the flowchart on a desktop-class machine; phone speed isn't measured. The demo below runs the same real library. Judge the layout shift yourself: nodes move as the graph grows, and a soft crossfade is all that's softening it.
